Adding a service

A new service touches DNS, security, monitoring and documentation, so it is added in one reviewed change. Nothing here may be skipped; "not applicable" needs a stated reason.

Requirements​

#RequirementWhere it is recorded
1Justify the hostname. Meet at least one test in When a subdomain is justified; otherwise use a pathADR or pull request description
2Add a catalogue entry to data/subdomains.jsonSubdomain catalogue
3Write a platform-service page with one responsibility and its boundariesdocs/services/platform/<slug>.md
4Set visibility and lifecycle explicitly. Default to restricted for anything that writes, integrates or managesCatalogue and page front matter
5Decide ownership. Name who maintains it and where the code livesService page
6Decide monitoring. State whether it has a health check and whether it appears on the status pageService page; Observability
7Review threats and access. Cover untrusted input, the shared session cookie, secrets and least privilegeSecurity, privacy and access
8Write deployment and rollback notes. Say how it is released and how it is reversedEnvironments and deployment model
9Update documentation and status in the same pull requestThis checklist

Steps​

  1. Open the pull request and describe the justification (requirement 1).

  2. Add the catalogue record. Use planned until the service is verified as running, and set evidence honestly.

    Catalogue record (illustrative)
    {
      "slug": "example",
      "hostname": "example.rjmlaird.co.uk",
      "title": "Example",
      "purpose": "One public-safe sentence",
      "classification": "integration",
      "visibility": "restricted",
      "lifecycle": "planned",
      "evidence": "none",
      "documentation": "services/platform/example.md",
      "publish": true,
      "status": null,
      "health": null,
      "repository": null
    }

  3. Create the service page. Give it visibility and lifecycle front matter that match the record, and link to shared pages instead of repeating their rules.

  4. Run pnpm run docs:generate, then pnpm run docs:check, and commit the regenerated table.

  5. Add the page to sidebars.ts in the right group.

  6. Build the site and fix any broken link before requesting review.

Never include​

Secrets, credentials, account or binding identifiers, bucket names, internal hostnames, private management or health URLs, and exact access-policy rules.

After launch​

Change lifecycle to active only when a repository or a check verifies the service, and update the page, the catalogue and the status page together. To retire a service, set retired, redirect or remove DNS in the same change, and record the decision.
